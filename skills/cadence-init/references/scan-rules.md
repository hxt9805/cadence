# 项目扫描策略

> 本文件供 project-scanner subagent 参考。定义通用发现、领域适配、项目快照和来源
> 不一致检测。软件只是支持的项目类型之一。

## 扫描原则

1. **先通用发现，后领域适配**：先观察已有材料，再决定使用哪些适配规则；不得仅凭
   缺少代码 manifest 就把项目视为空项目。
2. **项目主产物优先**：识别本项目真正交付、维护或用来判断进度的产物，而不是预设
   所有项目都以代码为中心。
3. **来源随问题变化**：事实的权威性取决于项目声明、问题相关性、直接性和新鲜度；
   手写文件不天然低可信，代码也不天然能回答所有问题。
4. **选择性读取**：只读足以建立快照的代表性材料，不全量复制正文，不读取秘密。

## 通用发现

优先检查：

| 来源 | 提取信息 |
|---|---|
| README、项目说明、brief、charter、proposal | 定位、目标、受众、完成标准 |
| 顶层目录与文件类型分布 | 项目结构、主要材料类型、可能的主产物 |
| plans、notes、docs、references、assets 等目录 | 计划、过程材料、参考资料、素材 |
| changelog、日志、时间线、版本历史 | 最近进展与状态变化 |
| 明确声明的 source-of-truth 文件 | 项目自己的权威来源规则 |
| Git 或其他可用版本历史 | 最近活跃区域；不可用时跳过 |

忽略依赖目录、缓存、构建输出、编辑器状态和系统临时文件。二进制文件默认只记录
安全元数据（路径、类型、大小、修改时间），除非有合适工具且读取确有必要。

## 领域适配器

适配器可以组合使用，不建立互斥 schema：

| 适配器 | 代表性来源 | 可提取事实 |
|---|---|---|
| 软件 | `package.json`、`pyproject.toml`、`src/`、配置、部署文件 | 技术栈、模块、运行约束、接口 |
| 研究 | 研究方案、数据字典、样本说明、实验记录、参考文献 | 问题、方法、样本边界、证据门槛 |
| 写作 | 提纲、稿件、素材、风格指南、编辑记录 | 结构、目标读者、版本、未决内容 |
| 学习 | 学习计划、课程材料、练习、学习记录、评估 | 目标、节奏、进度、完成标准 |
| 运营 | 运营计划、日历、预算、流程、看板导出、复盘 | 活动、责任、资源、状态、中止条件 |
| 通用 | 任意项目主产物与项目声明 | 目标、范围、约束、状态、依赖、待决 |

未识别的项目类型使用通用适配器，并在 `project_kind` 中写用户已有称呼或
`"General"`，不要硬猜。

## 项目快照模板

输出到 `cadence/discussions/00-project-snapshot.md`：

```markdown
# 项目现状快照（YYYY-MM-DD 扫描生成）

> ⚠️ 这是 cadence 自动生成的初版档案，可能有错漏。
> 请阅读后手动修正。标 [TBD] 的部分需要你补充。

## 规模概览
- 项目类型：...
- 主要材料：...
- 文件数：~N 个（不含依赖、缓存和构建输出）

## 一句话定位
[从 README 摘要，找不到则 [TBD]]

## 项目主产物
- ... [来源：...]

## 主要目录结构
[扫描顶层，列 2 层]

## 当前工作流与组织方式
[阶段、模块、章节、实验、课程或活动等；推断必须标注"推断"]

## 关键约束 / 外部依赖
[项目声明、配置、协议、预算、样本、时间或工具依赖]

## 已有材料摘要
- path/to/artifact: 简要摘要
- ...

## 项目意图（来源：xxx，YYYY-MM 撰写）
⚠️ 以下内容记录当时意图；是否仍成立需结合项目声明的权威来源与当前主产物验证
- ...

## 最近活跃区域
[基于可用版本历史、进度日志或材料修改时间]

## 未知 / 待补充
- 项目目标和目标用户：[TBD]
- 当前主产物与完成标准：[TBD]
- 已知风险或阻碍：[TBD]
- 历史关键决策：[TBD]

## 领域附录（仅在适用时）
[例如软件技术栈、研究方法、写作结构、学习评估或运营资源；无适用项则省略]
```

## 一致性检测规则

对比不同来源对同一事实或意图的说法，分**二级**：

- **🔴 关键**：会让后续 agent 或用户采取错误行动
  - 目标、范围、主产物或完成标准冲突
  - 关键规则、版本、样本边界、预算、时间或责任冲突
  - 项目声明的权威来源与当前材料明显不一致
- **⚪ 其他**：其他所有不一致
  - 次要描述、索引或示例过时
  - 不影响当前工作的结构细节差异

发现冲突时先标明双方来源、日期和直接证据。只有项目已声明某来源为权威，或一方
明显是另一方的生成/派生产物时，才建议以其为准；否则标为待确认，不替用户裁决。

## 不一致清单模板

输出到 `cadence/discussions/01-inconsistencies.md`：

```markdown
# 项目来源不一致清单

> cadence 扫描时识别。使用 `[ ]` 复选框标记处理状态。

## 🔴 关键（待处理 N / 已处理 M）

- [ ] **完成标准不一致：公开前是否需要复核**
  - 说法 A（project-brief.md L12）：完成初稿即可公开
  - 说法 B（review-checklist.md L8）：必须经过事实复核
  - 权威来源：[未声明]
  - 建议：由用户确认当前规则，再更新过时来源

- [ ] ...

## ⚪ 其他（待处理 N / 已处理 M，默认折叠）

<details>
<summary>展开查看</summary>

- [ ] ...

</details>

## ✓ 已处理 / 已忽略

（每次用户标记完成时移动到这里）
```

## 硬上限

- 不一致总条数：30 条。超出则截断，在清单末尾写：
  "⚠️ 另有 N 条中低优先级不一致未详细列出。修完现有再扫可查看。"

## 关键决策

- **问题相关性 + 项目声明 + 直接证据 + 新鲜度**共同决定权威性。
- **从不自动修改项目主产物、原始数据或已有材料**。只生成 cadence/ 下的档案。
- **每个事实字段要标注 [来源：xxx]**，让用户/Claude 判断可信度。
- **不把领域名称写死进通用 schema**。领域附录只在适用时出现。

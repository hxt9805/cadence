# 通用语义保真规则

> 当一个已被承接的决定需要写 streaming entry、做 handoff fidelity sweep 或整合
> canonical discussion 时读取。它适用于任何项目类型，不是软件开发专用模板。

## 核心公式

```text
承接决定是否记录
持久语义增量决定是否新建 entry
影响等级决定记录多详细
```

记录的是能改变或约束后续工作的稳定语义，不是聊天消息本身。

## 三段式记录判定

### 1. 承接

以下信号表示候选方案已被承接：

- 明确确认：可以、认可、同意、就这样；
- 选择方案：方案二、选 B、按你推荐的来；
- 隐含确认：直接要求按该方案继续实施、规划或讨论下一步。

用户明确说“不记录”时不写入。未被承接的探索方案不能写成 accepted decision。

### 2. 持久语义增量

命中至少一种才新建 entry：

- 目标、范围、非目标或完成标准变化；
- 方案、规则、顺序、阈值、责任或边界变化；
- 状态、关系、依赖、风险或待决问题变化；
- 一个以后可能重新出现的候选方案被否决；
- 既有决定被实施、撤回、替代或失效。

不新建 entry：

- 重复确认已记录内容；
- 寒暄、转场和进度询问；
- 没有影响最终结果的临时推测；
- 原始工具日志、长测试输出和可替代的原文；
- 尚未被承接的 brainstorming。

是否形成持久增量存在合理不确定性时，写 Light entry，不把判断负担交给用户。

### 3. 影响等级

先评估通用影响维度，再选择 Light / Standard / High。项目类型和领域名称不能决定
保真等级。

## 通用影响维度

| 维度 | 低影响 | 高影响 |
|---|---|---|
| 可逆性 | 可轻易撤回 | 难以撤回或不可逆 |
| 影响范围 | 单点、局部 | 跨阶段、跨参与者或跨产物 |
| 损失风险 | 失败代价低 | 可能损失数据、资金、信誉、隐私或大量时间 |
| 持续时间 | 临时选择 | 约束未来多个 session |
| 外部承诺 | 纯内部 | 涉及用户、客户、公众、法规或合同 |
| 不确定性 | 已知路径 | 假设多、失败模式复杂 |
| 协作复杂度 | 单人单步骤 | 多角色、多系统或多依赖 |

领域名称只能作为示例，不能成为固定 schema、唯一触发条件或必填字段。

## Light / Standard / High

### Light

适用：低影响、可逆、局部的稳定决定。

记录：

- `context`：为什么需要决定；
- `chosen`：决定及适用边界。

### Standard

适用：影响一个工作阶段、多个产物或后续讨论。

记录：

- `context`
- `chosen`
- `rationale`
- `alternatives_or_rejected`（仅当真实讨论过）
- `dependencies`
- `open_questions`

### High

适用：难逆、长周期、外部承诺明显、失败代价高或跨参与者的决定。

High 必须有：

- `context`
- `chosen`
- `rationale`

再从下列通用语义槽选择适用项：

- `scope_and_non_goals`
- `actors_and_responsibilities`
- `artifacts_or_entities`
- `rules_and_invariants`
- `states_and_transitions`
- `sequence_and_dependencies`
- `resources_and_limits`
- `access_and_boundaries`
- `failure_and_recovery`
- `retention_and_exit`
- `external_commitments`
- `evidence_and_acceptance`
- `alternatives_considered`
- `open_questions`
- `supersedes`

容易被误认为遗漏、但确实不适用的槽放入 `not_applicable`。不为填模板而虚构内容。

## 承接短句

用户只说“可以”“认可”“方案二”“按你推荐的来”时：

1. 找到短句明确指向的最近完整候选方案；
2. 记录对象是被承接方案的持久语义，不是承接短句本身；
3. 提取相对于现有档案的新规则、边界、理由和真实否决项；
4. 按通用影响维度选择 profile；
5. 短句可能指向多个候选方案时询问用户，不得猜测。

错误：

```yaml
chosen: 采用方案二
```

正确形状：

```yaml
context: 不同参与者会在不同时间接手，需要避免职责混淆。
chosen: 每个阶段指定唯一负责人；交接完成前原负责人仍对结果负责。
rationale: 让责任边界在跨 session 和跨参与者时保持清晰。
semantic_slots:
  actors_and_responsibilities:
    - 每个阶段只有一个最终负责人
  states_and_transitions:
    - 交接确认后责任才转移
```

## 来源与敏感信息

可用 provenance：

- `explicit`：用户或被承接方案明确表达；
- `synthesized`：不改变含义的结构化整理；
- `inferred`：模型推断，只能进入待确认内容。

`chosen` 不能仅来自 `inferred`。不能为了让记录“完整”而虚构 rationale、否决项或
外部承诺。

永不写入：

- 密码；
- 验证码；
- 访问令牌或刷新令牌；
- API 密钥、私钥和 Cookie；
- 不必要的真实个人信息；
- 可能包含秘密的完整工具日志。

长工具输出只记录结论、可信证据摘要和安全的产物路径。能用文件或提交引用的内容，
不要复制全文。

## 跨领域示例

下列示例使用同一组影响维度和 profile，不建立领域专属 schema：

| 场景 | 可能等级 | 应保留的语义 |
|---|---|---|
| 软件迁移 | High | 不变量、失败恢复、验收证据 |
| 研究公开 | High | 授权边界、外部承诺、撤回方式 |
| 写作结构 | Standard | 章节顺序、理由、未定标题 |
| 学习计划 | Standard/High | 长期节奏、中断恢复、完成标准 |
| 运营活动 | High | 预算边界、责任人、中止条件 |
| 简单文案 | Light | 使用场景、最终文案 |

研究、写作、学习、运营和软件只是例子；实际等级取决于影响维度。

## 冷启动检查

整合或 handoff 前，假设新 session 看不到旧对话，仅靠 cadence 档案回答：

1. 已决定什么？
2. 为什么？
3. 否决过什么？
4. 哪些约束不能破坏？
5. 哪些问题仍未决定？
6. 下一步是什么？

相关问题确实不适用时可以明确说明；回答不出来且会影响继续工作时，保真状态必须是
`partial`，不能以摘要顺畅为由标记 `complete`。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 把“用户认可方案二”当决定 | 回溯并提取方案二的稳定语义 |
| 所有决定都套 High 大模板 | 按通用影响维度选择 profile |
| 因项目不是软件而降低保真度 | 只看影响，不看领域名称 |
| 复制聊天和工具输出 | 保存语义增量与产物路径 |
| 为填满字段推断用户意图 | 标 inferred 并放待确认 |
| 漏记后要求用户重新整理 | 范围明确时自动补记并告知 |
